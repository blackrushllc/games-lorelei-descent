# JUNIE TASK — LORELEI: DESCENT
## Step 10.2.1 — Generous Robot Hit Detection

### Objective

Correct a remaining combat collision problem reported during actual browser gameplay.

Step 10.2 successfully corrected the visible firing origins of Blackrush and the Sentinel robots, but the developer still has to aim energy bolts near enemy robots' feet to kill them. The same problem affects Blackrush's thrown axe: it must strike near the Armored Robot's feet to remove its armor.

This remains true despite introducing `getTargetRegion()` and centralized combat offsets.

**The desired result is deliberately generous arcade-style hit detection.**

A shot passing through or reasonably close to an ordinary robot's visible body should register. Slightly oversized hit regions are preferable to undersized ones.

Do not rebalance the enemies to compensate. We will increase enemy density and orchestrate more intense encounters in future milestones.

### 1. Find the actual cause

First inspect the complete collision chain in:

```text
src/config/combatConfig.js
src/entities/Blackrush.js
src/entities/Robot.js
src/systems/WeaponSystem.js
src/systems/CombatSystem.js
src/scenes/GameScene.js
```

And any other code involved in force-bolt or thrown-axe hit registration.

Step 10.2 added upper-body target regions, but those calculations have not produced the desired behavior.

Determine whether an existing Arcade Physics overlap/collider callback still requires a projectile to touch the robot's smaller, ground-centered physics body before a hit can be registered.

If so, the logical target region is effectively being ignored outside that small preliminary collision area.

Also investigate:

- Incorrect world-space target offsets.
- Mismatches between sprite anchor and logical entity coordinates.
- Projectile trajectory versus the displayed artwork.
- Separate collision mechanisms for force bolts and axes.
- Fast-moving projectiles passing through target regions between physics updates.

Do not assume the first hypothesis is correct without tracing the actual code.

### 2. Separate movement collision from combat collision

The robot's navigation and movement collision body should not dictate how easily it can be shot.

Keep the existing movement body stable.

Introduce or correct the effective combat target volume independently.

Both energy bolts and axes must be able to hit that volume without requiring an earlier overlap with a smaller feet-centered body.

Possible implementations include:

- Dedicated combat collision sensors.
- Explicit projectile-versus-target geometric checks.
- A shared swept projectile collision system.

Choose the smallest reliable solution that fits the existing architecture.

Do not resize robot movement bodies in a way that breaks navigation, obstacles, or crowd behavior.

### 3. Generous target regions

For ordinary robots, use a configurable target region centered on the substantial visible body rather than the ground anchor.

Include the head, torso, and a generous margin around the sides.

A vertically oriented ellipse, circle, or rectangle is acceptable.

Favor forgiveness over precision.

As a starting point, use a target area approximately 20–35% more generous than the perceived solid-body silhouette, with adjustments as needed after visual testing.

These percentages are tuning guidance, not an instruction to scale the entire source PNG, including transparent padding.

The target region must remain stable when the robot changes animation, direction, or visual state.

Use archetype-specific configuration only where genuinely necessary.

### 4. Projectile collision behavior

Blackrush's energy bolts should register a hit when their actual world-space paths intersect the generous robot target region.

If projectiles travel fast enough to cross a region between updates, implement swept collision detection using the previous and current projectile positions.

Avoid tunneling.

A shot passing through the robot's upper torso should register regardless of whether it overlaps the old physics body near the feet.

Maintain correct projectile destruction and prevent duplicate damage from a single impact.

Preserve existing damage, rate of fire, projectile speed, and scoring.

### 5. Thrown axe versus Armored Robot

Apply the same generous collision principles to the axe.

A thrown axe striking anywhere reasonably close to the armored robot's visible body should remove its armor.

It should not need to strike the robot's feet.

Preserve the existing armored-to-disarmed transition.

Do not change the required number of hits, damage rules, or vulnerability progression.

Ensure an axe cannot trigger the armor-removal event multiple times during a single collision.

This milestone is not intended to add new armor-break particles or sound effects.

### 6. Keep environmental cover meaningful

Making robots easier to hit must not allow shots to pass through solid cover.

Preserve existing obstacle and cover collision rules.

When a projectile crosses both an obstacle and a robot target region within one update, resolve the earliest valid intersection along its travel path.

Do not award a hit through cover merely because an enlarged target region intersects a wall.

Avoid allowing overly generous hitboxes to extend through nearby solid obstacles in ways that produce unfair hits.

### 7. Preserve boss mechanics

The Proxy and Giant Boss have specialized component-based damage systems.

Do not replace those mechanics with generic enlarged hitboxes.

Do not alter boss damage stages, weak points, or authored music cues.

This change is specifically for the ordinary robots:

- Pursuer.
- Sentinel.
- Armored Pursuer.

Preserve their existing archetype-specific damage behavior.

### 8. Performance

This game is intended to feature increasingly large numbers of robots.

Any new hit-detection approach must remain efficient when many robots and projectiles are active.

Avoid excessive allocations inside per-frame collision loops.

Use spatial filtering or broad-phase candidate checks where useful, but ensure those checks encompass the full generous target region.

Do not introduce an expensive full-world scan for every projectile if a more efficient existing mechanism is available.

### 9. Combat geometry debug overlay

Step 10.2 introduced a developer control called `TOGGLE GEOMETRY`.

Extend or correct this visualization to show the **actual effective combat collision regions** rather than merely displaying configuration values.

For each robot, the overlay should distinguish:

- Ground position.
- Movement physics body.
- Combat target region.
- Target center.

The displayed combat region must correspond to the geometry that can actually cause damage.

If a debug overlay shows an enlarged target area but projectiles still pass through it harmlessly, that is a failed implementation.

This diagnostic is important for manual testing.

### 10. Tests

Create focused regression tests proving actual collision behavior, not merely verifying configuration numbers.

Test the following:

1. A bolt passing through a Pursuer's upper torso registers a hit.
2. A bolt passing near the Pursuer's shoulder within the generous region registers.
3. A bolt passing through a Sentinel's upper torso registers.
4. An axe passing through an Armored Robot's upper body removes armor.
5. These hits register without requiring an overlap with the ground-centered movement physics body.
6. A projectile passing completely outside the generous target region misses.
7. High-speed projectiles do not tunnel through robots.
8. A projectile cannot damage the same robot twice from one collision event.
9. A wall between projectile and robot blocks the attack.
10. Changing sprite direction does not move the combat region.
11. Changing armored/disarmed visual state does not shift the target region.
12. Normal robot movement and navigation remain unchanged.
13. NOVA behavior remains unchanged.
14. Existing laser attack geometry remains unchanged.
15. Existing boss weak-point collision remains unchanged.
16. Restart and checkpoint reconstruction do not create duplicate combat sensors.

Use representative projectile paths passing through different heights on a standing robot.

Run:

```bash
npm test
npm run build
```

Test shots passing close to robots and shots blocked by cover.

Also confirm normal gameplay still works with PIXEL ART disabled.

If browser testing is unavailable, explicitly mark it pending.
