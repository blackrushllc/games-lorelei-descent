## Step 10.0.1 — Variable-Resolution Sprite Frames and Stable Animation Anchoring

### Objective

Correct the Step 10.0 sprite pipeline's assumptions about source PNG dimensions.

PixelLab produces animation frames whose PNG canvas dimensions vary by character, animation, direction, and visual damage state.

These variations are intentional and must be supported without resizing, clipping, distorting, or discarding the original artwork.

The developer has successfully run `npm run sprites`, generating atlas pages and a v2 manifest for all 10 entities, but the compiler emitted 1,884 repetitive dimension warnings.

Do not begin additional character integration.

This is a focused asset-pipeline correction.

### 2. Critical policy: preserve PixelLab artwork

The source PNG files are authoritative for their pixel dimensions.

Never automatically resize a source PNG to the old `expectedFrameSize`.

Never crop portions of animation frames simply to fit a nominal character size.

Do not stretch frames.

Do not automatically scale an 80×80 frame down to 48×48.

Do not assume a larger canvas means a physically larger character.

Maintain original pixel detail, transparency, and nearest-neighbor rendering.

Any padding or alignment processing must preserve source pixels unchanged.

The project should distinguish:

- Original PNG canvas dimensions.
- Actual nontransparent content bounds.
- Render alignment/pivot.
- Desired in-game display scale.
- Physics collision geometry.

These are separate properties.

### 4. Variable source dimensions

Update the compiler to accept varying native PNG dimensions.

Every frame must retain its actual source width and height in the output metadata.

Support differing dimensions:

- Across entities.
- Across visual states.
- Across animation types.
- Across directions.
- Between frames of one animation, if present.

Do not require square images.

Use per-frame rectangle dimensions when packing atlases.

Do not use a fixed frame grid that assumes all source frames have identical dimensions.

Continue supporting atlas paging.

A frame must never be clipped because it is larger than the nominal entity size.

### 5. Stable visual pivot and grounding

This requirement is particularly important.

Changing from idle to walk, run, throw, swing, or collapse must not cause an entity to jump around merely because its PNG canvas dimensions differ.

Implement a stable visual anchoring policy.

Preferred model:

- The entity's world position is the authoritative gameplay position.
- The visual sprite is positioned relative to that world position.
- A logical pivot identifies the character's grounded location or another deliberate attachment point.
- Different-sized source canvases align to the same logical pivot.

For standing and walking humanoids, an approximate feet-center or ground-contact reference is appropriate.

For robots, use a consistent base/ground-contact reference.

For bosses, allow an entity-specific pivot.

For collapsing and burning animations, allow state-specific overrides.

Investigate the source PNGs' transparency and alignment.

A possible approach is to derive useful alpha-content bounds and use them to establish reference pivots, but do not independently recenter every animation frame in a way that makes the character's torso, feet, or body jitter.

Prefer stable reference pivots across a sequence.

Provide configurable overrides where automated alignment is insufficient.

Do not invent arbitrary per-frame offsets without inspection.

### 6. Preserve apparent physical scale

The apparent size of Blackrush must remain broadly stable when switching:

```text
idle -> walk -> run -> force-run -> axe-throw
```

A larger PNG canvas should not, by itself, make Blackrush physically grow.

Similarly:

- Eclipse crouching must not cause her scale to jump.
- German Soldier throwing must not cause sudden enlargement.
- Armored Robot switching to disarmed artwork must not cause accidental resizing.
- Proxy damage states should retain consistent boss proportions.
- Giant Boss damage states should retain consistent boss proportions until an intentional collapse or destruction effect.

Preserve source pixel dimensions.

Use an explicit entity-level display scale and visual alignment parameters rather than scaling every frame according to its canvas dimensions.

If PixelLab artwork itself genuinely changes its illustrated body size between animations, report that as a source-art issue rather than trying to conceal it using arbitrary runtime resizing.

Do not break existing animation IDs or the generic runtime `resolve()` API.

### 9. Warning and validation policy

The existing log emitted 1,884 warnings, predominantly repeating the same message hundreds of times.

Replace these repetitive messages with grouped, useful diagnostics.

Dimension differences should be accepted when the pipeline supports them.

For example:

```text
[SPRITES] blackrush
  48x48: 16 frames
  64x64: 161 frames
  68x68: 152 frames
  80x80: 64 frames
  Mixed canvas dimensions: SUPPORTED
```

Use actual measured counts in real reports.

Do not repeat the same warning for every frame.

Remain strict about genuine errors:

- Invalid or unreadable PNG.
- Zero-sized frame.
- Broken animation sequence.
- Missing required direction.
- Duplicate frame identifier.
- Invalid atlas rectangle.
- Missing atlas page.
- Incorrect frame reference.
- Cropped artwork.
- Invalid or circular fallback.
- Other actual pipeline corruption.

Unexpectedly extreme dimensions may produce a concise warning, but should not cause automatic resizing.

Report dimensions by entity and, where useful, by state and animation.
